## Цель

Научиться проектировать property graph от пользовательских вопросов: выбирать узлы, метки, свойства и направленные отношения, создавать граф в Neo4j через MERGE и писать запросы Cypher, включая многошаговые обходы.

## Предметная область

Небольшой интернет-магазин электроники и книг. Покупатели смотрят карточки товаров и покупают их. Товары лежат в категориях, категории образуют дерево (Аксессуары входят в Электронику, Программирование входит в Книги).

Пользователи: покупатель (смотрит каталог, свои покупки, получает рекомендации), менеджер магазина (смотрит что покупают, выручку по категориям, кто смотрел товар и не купил).

Все данные учебные, имена и покупки выдуманные.

## Паттерны доступа

| | Вопрос | Кто | Чтение/запись | Нужен обход по связям |
|---|---|---|---|---|
| Q1 | список товаров, товары дешевле X, самые дорогие | покупатель | чтение, часто | нет, фильтр по свойствам |
| Q2 | что купил конкретный покупатель | покупатель, менеджер | чтение, часто | 1 шаг: Customer -> Product |
| Q3 | товары в категории, включая подкатегории | покупатель | чтение, очень часто | 1 шаг + дерево категорий переменной длины |
| Q4 | рекомендации: кто купил то же, что и я, купили еще | покупатель | чтение, часто | 3 шага: я -> товар <- другой -> товар |
| Q5 | смотрел, но не купил | менеджер | чтение, раз в день | 1 шаг + проверка отсутствия ребра |
| Q6 | сколько раз купили товар, выручка по категориям | менеджер | чтение, редко | агрегация по ребрам |
| Q7 | товары, связанные через покупки (повышенное) | менеджер | чтение, редко | путь переменной длины по BOUGHT |
| W | покупка, просмотр, смена цены | приложение | запись, часто | создать ребро / изменить свойство |

Главный паттерн - Q3 и Q4: это то, что показывается на каждой карточке товара и на главной странице.

## Почему граф, а не документы

В документной модели (как в лабах 1-4 на MongoDB) товар был бы документом, а покупки либо массивом `bought: [sku, sku]` внутри покупателя, либо отдельной коллекцией orders. Для Q1, Q2 и Q6 этого хватает: один find или aggregate.

Проблемы начинаются на Q3, Q4, Q7:
- рекомендации "кто купил то же, что и я" - это два $lookup подряд (purchases -> покупатели -> их purchases) и $unwind, запрос раздувается в декартово произведение, а на большой коллекции будет медленным
- дерево категорий произвольной глубины - в MongoDB это $graphLookup или рекурсия в приложении
- "товары на расстоянии 2-4 покупок" документной моделью без цикла в приложении вообще не делается

В Neo4j все это записывается одним шаблоном, а переход по ребру - это переход по указателю, он не зависит от размера всей базы, только от числа соседей. Поэтому для вопросов про связи (рекомендации, категории, похожие товары) граф подходит лучше. Если бы магазину нужен был только каталог и история заказов, документная модель была бы проще.

## Схема графа

Узлы:

| Label | Уникальный id | Свойства |
|---|---|---|
| Customer | customerId (int) | name, city |
| Product | sku (string) | title, price (тенге) |
| Category | name | - |

Отношения (все направленные):

| Тип | Откуда -> Куда | Свойства | Почему так направлено |
|---|---|---|---|
| BOUGHT | Customer -> Product | date, qty | покупатель купил товар, читается как предложение |
| VIEWED | Customer -> Product | date | покупатель посмотрел товар |
| BELONGS_TO | Product -> Category | - | товар принадлежит категории |
| PART_OF | Category -> Category | - | подкатегория входит в родительскую, стрелка к корню |

PART_OF добавил сверх варианта, чтобы категории были деревом и было по чему делать обход переменной длины.

Пример пути (рекомендация):
```
(:Customer {customerId:1001})-[:BOUGHT]->(:Product)<-[:BOUGHT]-(:Customer)-[:BOUGHT]->(:Product)
```
Пример пути (товар до корневой категории):
```
(:Product {sku:'P-004'})-[:BELONGS_TO]->(:Category {name:'Аксессуары'})-[:PART_OF]->(:Category {name:'Электроника'})
```

Дата и количество - свойства ребра BOUGHT, а не отдельный узел Order, потому что в этой лабе заказ ни с чем больше не связан. Если появятся доставка, оплата, несколько товаров в одном заказе, то Order станет узлом.

Ограничения на уникальность, чтобы MERGE не плодил дубли и поиск по id шел через индекс:
```
CREATE CONSTRAINT customer_id IF NOT EXISTS FOR (c:Customer) REQUIRE c.customerId IS UNIQUE;
CREATE CONSTRAINT product_sku IF NOT EXISTS FOR (p:Product) REQUIRE p.sku IS UNIQUE;
CREATE CONSTRAINT category_name IF NOT EXISTS FOR (c:Category) REQUIRE c.name IS UNIQUE;
```
```
+-----------------------------------------------------------------+
| name            | type         | labelsOrTypes | properties     |
+-----------------------------------------------------------------+
| "category_name" | "UNIQUENESS" | ["Category"]  | ["name"]       |
| "customer_id"   | "UNIQUENESS" | ["Customer"]  | ["customerId"] |
| "product_sku"   | "UNIQUENESS" | ["Product"]   | ["sku"]        |
+-----------------------------------------------------------------+
```

## Создание графа

5 покупателей, 8 товаров, 6 категорий = 19 узлов. 13 BOUGHT, 8 VIEWED, 8 BELONGS_TO, 4 PART_OF = 33 отношения.

Узлы через MERGE по уникальному ключу, остальные свойства через SET:
```
MERGE (:Customer {customerId: 1001, name: 'Айдар С.', city: 'Алматы'});
MERGE (:Category {name: 'Электроника'});
MERGE (p:Product {sku: 'P-001'}) SET p.title = 'Ноутбук IdeaPad 3 15"', p.price = 289990;
```
Отношения: сначала MATCH обоих узлов, потом MERGE ребра, чтобы при повторном запуске ничего не дублировалось:
```
MATCH (a:Category {name: 'Аксессуары'}), (b:Category {name: 'Электроника'}) MERGE (a)-[:PART_OF]->(b);
MATCH (p:Product {sku: 'P-004'}), (c:Category {name: 'Аксессуары'}) MERGE (p)-[:BELONGS_TO]->(c);
MATCH (c:Customer {customerId: 1001}), (p:Product {sku: 'P-001'}) MERGE (c)-[:BOUGHT {date: date('2026-09-02'), qty: 1}]->(p);
MATCH (c:Customer {customerId: 1001}), (p:Product {sku: 'P-002'}) MERGE (c)-[:VIEWED {date: date('2026-10-04')}]->(p);
```
Остальные в queries.cypher.

Проверка структуры:
```
MATCH (n) RETURN labels(n) AS labels, count(*) AS qty ORDER BY labels;
MATCH ()-[r]->() RETURN type(r) AS relation, count(*) AS qty ORDER BY relation;
```
```
+--------------------+      +--------------------+
| labels       | qty |      | relation     | qty |
+--------------------+      +--------------------+
| ["Category"] | 6   |      | "BELONGS_TO" | 8   |
| ["Customer"] | 5   |      | "BOUGHT"     | 13  |
| ["Product"]  | 8   |      | "PART_OF"    | 4   |
+--------------------+      | "VIEWED"     | 8   |
                            +--------------------+
```

Проверил, что constraint работает. CREATE покупателя с существующим id:
```
CREATE (:Customer {customerId: 1001, name: 'Дубль'});
```
```
Node(0) already exists with label `Customer` and property `customerId` = 1001
```
А MERGE по тому же ключу просто находит узел и ничего не создает:
```
MERGE (c:Customer {customerId: 1001}) RETURN c.customerId, c.name;
```
```
| 1001         | "Айдар С." |
```
Покупателей так и осталось 5.

## Q2 - запрос по отношению: что купил Айдар

```
MATCH (c:Customer {customerId: 1001})-[b:BOUGHT]->(p:Product)
RETURN p.sku AS sku, p.title AS title, b.date AS date, b.qty AS qty ORDER BY b.date;
```
```
+-------------------------------------------------------+
| sku     | title                    | date       | qty |
+-------------------------------------------------------+
| "P-003" | "Клавиатура MX Keys"     | 2026-09-02 | 1   |
| "P-001" | "Ноутбук IdeaPad 3 15\"" | 2026-09-02 | 1   |
| "P-006" | "Книга «Чистый код»"     | 2026-09-15 | 1   |
```

## Q3 - двухшаговый обход: рекомендации для Айдара

"Те, кто купил то же, что и я, купили еще":
```
MATCH (me:Customer {customerId: 1001})-[:BOUGHT]->(p:Product)<-[:BOUGHT]-(other:Customer)-[:BOUGHT]->(rec:Product)
WHERE other <> me AND NOT (me)-[:BOUGHT]->(rec)
RETURN rec.sku AS sku, rec.title AS title, count(DISTINCT other) AS buyers, collect(DISTINCT other.name) AS who
ORDER BY buyers DESC, sku;
```
```
+--------------------------------------------------------------------------+
| sku     | title                       | buyers | who                     |
+--------------------------------------------------------------------------+
| "P-007" | "Книга «Грокаем алгоритмы»" | 2      | ["Алия К.", "Ерлан Б."] |
| "P-002" | "Наушники WH-1000XM5"       | 1      | ["Дана Н."]             |
| "P-004" | "Мышь MX Master 3S"         | 1      | ["Ерлан Б."]            |
| "P-005" | "Чехол для ноутбука 15\""   | 1      | ["Дана Н."]             |
+--------------------------------------------------------------------------+
```
Путь: Айдар -> его товар <- другой покупатель -> его другой товар. `other <> me` убирает самого Айдара (он ведь тоже купил p), `NOT (me)-[:BOUGHT]->(rec)` убирает то, что у него уже есть. «Грокаем алгоритмы» на первом месте, потому что к ней ведут два пути: через Алию (общая книга «Чистый код») и через Ерлана (общая клавиатура).

Смотрел, но не купил:
```
MATCH (c:Customer)-[v:VIEWED]->(p:Product)
WHERE NOT (c)-[:BOUGHT]->(p)
RETURN c.name AS customer, p.title AS product, v.date AS viewed ORDER BY viewed;
```
```
+------------------------------------------------------+
| customer    | product                   | viewed     |
+------------------------------------------------------+
| "Айдар С."  | "Мышь MX Master 3S"       | 2026-09-02 |
| "Ерлан Б."  | "Ноутбук IdeaPad 3 15\""  | 2026-09-20 |
| "Алия К."   | "Ноутбук IdeaPad 3 15\""  | 2026-09-25 |
| "Дана Н."   | "Колонка Flip 6"          | 2026-10-01 |
| "Мадина Т." | "Ноутбук IdeaPad 3 15\""  | 2026-10-03 |
| "Айдар С."  | "Наушники WH-1000XM5"     | 2026-10-04 |
| "Мадина Т." | "Мышь MX Master 3S"       | 2026-10-06 |
| "Ерлан Б."  | "Чехол для ноутбука 15\"" | 2026-10-10 |
+------------------------------------------------------+
```
Все 8 просмотров попали, потому что в моих данных никто не смотрел то, что потом купил. Ноутбук смотрели трое и не купили - менеджеру повод подумать о цене.

## Q4 - обход переменной длины: товары в Электронике с подкатегориями

```
MATCH (p:Product)-[:BELONGS_TO]->(:Category)-[:PART_OF*0..3]->(root:Category {name: 'Электроника'})
RETURN p.sku AS sku, p.title AS title ORDER BY sku;
```
```
+-------------------------------------+
| sku     | title                     |
+-------------------------------------+
| "P-001" | "Ноутбук IdeaPad 3 15\""  |
| "P-002" | "Наушники WH-1000XM5"     |
| "P-003" | "Клавиатура MX Keys"      |
| "P-004" | "Мышь MX Master 3S"       |
| "P-005" | "Чехол для ноутбука 15\"" |
| "P-008" | "Колонка Flip 6"          |
+-------------------------------------+
```
`*0..3` - от 0 до 3 ребер PART_OF. 0 нужен на случай, если товар лежит прямо в корневой категории. Книги не попали, у них другой корень. Глубина 3 ограничена специально: дерево категорий в магазине глубже 3-4 уровней не бывает, а без границы запрос мог бы обойти весь граф.

Хлебные крошки для товара:
```
MATCH path = (p:Product {sku: 'P-004'})-[:BELONGS_TO]->(:Category)-[:PART_OF*0..3]->(root:Category)
WHERE NOT (root)-[:PART_OF]->()
RETURN p.title AS title, [n IN nodes(path)[1..] | n.name] AS breadcrumb, length(path) AS hops;
```
```
+------------------------------------------------------------+
| title               | breadcrumb                    | hops |
+------------------------------------------------------------+
| "Мышь MX Master 3S" | ["Аксессуары", "Электроника"] | 2    |
+------------------------------------------------------------+
```
`WHERE NOT (root)-[:PART_OF]->()` оставляет только путь до корня, иначе вернулись бы и промежуточные.

## Повышенное задание - товары, связанные через покупки

Товары, которые покупали вместе с ноутбуком (длина пути 2, один общий покупатель):
```
MATCH (p:Product {sku: 'P-001'})<-[:BOUGHT]-(c:Customer)-[:BOUGHT]->(other:Product)
RETURN other.sku AS sku, other.title AS title, collect(c.name) AS via ORDER BY sku;
```
```
+----------------------------------------------------+
| sku     | title                     | via          |
+----------------------------------------------------+
| "P-002" | "Наушники WH-1000XM5"     | ["Дана Н."]  |
| "P-003" | "Клавиатура MX Keys"      | ["Айдар С."] |
| "P-005" | "Чехол для ноутбука 15\"" | ["Дана Н."]  |
| "P-006" | "Книга «Чистый код»"      | ["Айдар С."] |
+----------------------------------------------------+
```

Ограниченный путь 1..3 по ребрам BOUGHT без направления - что вообще достижимо от ноутбука:
```
MATCH path = (p:Product {sku: 'P-001'})-[:BOUGHT*1..3]-(x)
RETURN length(path) AS hops, labels(x)[0] AS label, coalesce(x.title, x.name) AS reached, count(path) AS paths
ORDER BY hops, reached;
```
```
+-------------------------------------------------------+
| hops | label      | reached                   | paths |
+-------------------------------------------------------+
| 1    | "Customer" | "Айдар С."                | 1     |
| 1    | "Customer" | "Дана Н."                 | 1     |
| 2    | "Product"  | "Клавиатура MX Keys"      | 1     |
| 2    | "Product"  | "Книга «Чистый код»"      | 1     |
| 2    | "Product"  | "Наушники WH-1000XM5"     | 1     |
| 2    | "Product"  | "Чехол для ноутбука 15\"" | 1     |
| 3    | "Customer" | "Алия К."                 | 1     |
| 3    | "Customer" | "Ерлан Б."                | 1     |
| 3    | "Customer" | "Мадина Т."               | 1     |
+-------------------------------------------------------+
```
Граф двудольный: BOUGHT всегда соединяет Customer и Product, поэтому на нечетных шагах покупатели, на четных товары. 1 шаг - кто купил ноутбук, 2 - что они еще купили, 3 - кто еще покупал эти товары (похожие покупатели). Без направления, потому что путь идет то по стрелке, то против.

Отсюда "товары, связанные через покупки" - это четные длины, до 4 (два покупателя между товарами):
```
MATCH path = (p:Product {sku: 'P-001'})-[:BOUGHT*2..4]-(other:Product)
WHERE other <> p
RETURN other.title AS title, min(length(path)) AS min_hops, count(path) AS paths
ORDER BY min_hops, paths DESC;
```
```
+------------------------------------------------+
| title                       | min_hops | paths |
+------------------------------------------------+
| "Клавиатура MX Keys"        | 2        | 1     |
| "Книга «Чистый код»"        | 2        | 1     |
| "Чехол для ноутбука 15\""   | 2        | 1     |
| "Наушники WH-1000XM5"       | 2        | 1     |
| "Книга «Грокаем алгоритмы»" | 4        | 2     |
| "Мышь MX Master 3S"         | 4        | 1     |
| "Колонка Flip 6"            | 4        | 1     |
+------------------------------------------------+
```
На расстоянии 2 - прямые соседи по корзине, на расстоянии 4 - то, что покупали "похожие" покупатели. «Грокаем алгоритмы» связана двумя путями, значит ближе остальных. Если поставить `*2..6`, на моих 19 узлах уже дойдет до всего графа, поэтому граница 4 - разумная.

## Изменение

Скидка на наушники. До:
```
MATCH (p:Product {sku: 'P-002'}) RETURN p.title AS title, p.price AS price;
```
```
| "Наушники WH-1000XM5" | 149990 |
```
```
MATCH (p:Product {sku: 'P-002'}) SET p.price = 129990, p.discount = true
RETURN p.title AS title, p.price AS price, p.discount AS discount;
```
Контрольный MATCH после:
```
MATCH (p:Product {sku: 'P-002'}) RETURN p.title AS title, p.price AS price, p.discount AS discount;
```
```
+-------------------------------------------+
| title                 | price  | discount |
+-------------------------------------------+
| "Наушники WH-1000XM5" | 129990 | TRUE     |
+-------------------------------------------+
```
Свойство discount раньше не было, SET его просто добавил - схемы у узлов нет.

Свойство отношения: Ерлан купил не 2, а 1 книгу:
```
MATCH (c:Customer {customerId: 1003})-[b:BOUGHT]->(p:Product {sku: 'P-007'}) SET b.qty = 1
RETURN c.name AS customer, p.title AS title, b.qty AS qty;
```
```
| "Ерлан Б." | "Книга «Грокаем алгоритмы»" | 1   |
```

## Безопасное удаление

Удаляю старый просмотр мыши Айдаром. Сначала смотрю, что выберется:
```
MATCH (c:Customer {customerId: 1001})-[v:VIEWED]->(p:Product {sku: 'P-004'})
RETURN c.name AS customer, type(v) AS rel, v.date AS date, p.title AS product;
```
```
+----------------------------------------------------------+
| customer   | rel      | date       | product             |
+----------------------------------------------------------+
| "Айдар С." | "VIEWED" | 2026-09-02 | "Мышь MX Master 3S" |
+----------------------------------------------------------+
```
Одна связь, та самая. Удаляю и проверяю:
```
MATCH (c:Customer {customerId: 1001})-[v:VIEWED]->(p:Product {sku: 'P-004'}) DELETE v;
MATCH (c:Customer {customerId: 1001})-[v:VIEWED]->(p:Product {sku: 'P-004'}) RETURN count(v) AS left;
```
```
Deleted 1 relationships
| left | 0 |
```
Остальные просмотры Айдара на месте (наушники, 2026-10-04).

Удаление узла. Создал тестовый товар со связью в категорию и попробовал обычный DELETE:
```
MATCH (c:Category {name: 'Аксессуары'}) CREATE (t:Product {sku: 'TEST-1', title: 'Тестовый товар', price: 1})-[:BELONGS_TO]->(c);
MATCH (t:Product {sku: 'TEST-1'})-[r]->(x) RETURN t.sku AS sku, type(r) AS rel, x.name AS to;
MATCH (t:Product {sku: 'TEST-1'}) DELETE t;
```
```
| "TEST-1" | "BELONGS_TO" | "Аксессуары" |
Cannot delete node<19>, because it still has relationships. To delete this node, you must first delete its relationships.
```
Neo4j не дает оставить висячие ребра. Нужен DETACH DELETE:
```
MATCH (t:Product {sku: 'TEST-1'}) DETACH DELETE t;
MATCH (t:Product {sku: 'TEST-1'}) RETURN count(t) AS left;
```
```
Deleted 1 nodes, Deleted 1 relationships
| left | 0 |
```
В итоге в графе 19 узлов и 32 отношения (было 33, минус один VIEWED).

## Анализ

Производительность. Поиск по sku идет через уникальный индекс от constraint:
```
PROFILE MATCH (p:Product {sku: 'P-001'}) RETURN p.title;
```
```
| +NodeUniqueIndexSeek | UNIQUE p:Product(sku) WHERE sku = $autostring_0 | DB Hits 2 |
Total database accesses: 3
```
А поиск по title, на котором индекса нет, сканирует все узлы с меткой:
```
PROFILE MATCH (p:Product {title: 'Клавиатура MX Keys'}) RETURN p.sku;
```
```
| +Filter          | p.title = $autostring_0 | DB Hits 8 |
| +NodeByLabelScan | p:Product               | DB Hits 9 |
Total database accesses: 18
```
На 8 товарах разница 3 против 18, на миллионе товаров скан по метке станет проблемой, поэтому все точки входа в запрос (customerId, sku, name категории) должны быть под индексом. Дальше от точки входа обход идет по ребрам и от размера базы уже не зависит.

Эффективные запросы: Q2 (один шаг от индексированного узла), Q4 по категориям (от 1 узла категории вниз по дереву, товаров в подкатегории ограниченное число).

Дорогие запросы при росте:
- Q3 рекомендации. Если товар популярный (ноутбук купили 100 тысяч человек), шаг `<-[:BOUGHT]-(other)` раскроет 100 тысяч узлов, а следующий шаг еще по 10-50 товаров на каждого. Это супер-узел. Решение: ограничивать выборку (`LIMIT` после первого шага, брать только покупки за последний месяц через `WHERE b.date > ...`) или считать рекомендации заранее и хранить готовое ребро `(:Product)-[:ALSO_BOUGHT {score}]->(:Product)`
- путь `*2..4` по BOUGHT. На большом графе за 4 шага через популярные товары достижимо почти все, количество путей растет взрывом. Поэтому глубина не больше 4 и лучше брать `shortestPath` или ограничивать по дате
- агрегация выручки по всем покупкам - это полный проход по всем ребрам BOUGHT, для отчетов нормально, для карточки товара нет

Избыточные связи. VIEWED растет быстрее всего: просмотров в сотни раз больше, чем покупок, и один покупатель за день может насмотреть сотни ребер. Хранить их все в графе навсегда не стоит, лучше оставлять последние N или за 30 дней, а полную историю просмотров писать в Cassandra или лог. Ребро ALSO_BOUGHT (если делать предрасчет) - тоже избыточное, оно выводится из BOUGHT, за него платим рассинхронизацией.

Дубли узлов возможны, если загружать покупателей по имени: два Айдара С. - это два разных узла. Поэтому MERGE только по customerId и sku, и на них стоят constraint. Категории уникальны по имени, что при росте каталога спорно (две разные "Аксессуары" в разных корнях) - тогда нужен свой id.

Ограничения модели: в property graph нет схемы, можно случайно написать `BOUGH` или `custId` и запрос тихо вернет пустоту. Нет транзакций на несколько заказов как в SQL-отчетности, тяжелые агрегаты по всему графу медленнее, чем в колоночной базе. Для простого каталога без рекомендаций граф избыточен.

Масштабирование. Community-версия - один сервер, граф должен помещаться в память. При росте: сначала вертикально (больше RAM под page cache), потом читающие реплики (Enterprise causal cluster). Шардировать граф тяжело, потому что ребра пересекают шарды. Разумный вариант разделения - по доменам: каталог с категориями и покупки в Neo4j, просмотры и логи отдельно, рассчитанные рекомендации в Redis как кэш (как в лабе 5). Граф хранит только то, по чему реально нужно ходить.

## Relationship vs список id в документе (необязательное задание)

Взял обход Q3 (рекомендации) и сравнил два варианта хранения связи "купил":

| | (A) ребро BOUGHT в Neo4j | (B) массив `bought: ['P-001', 'P-003']` в документе покупателя |
|---|---|---|
| чтение "что купил" | 1 шаг, быстро | еще быстрее, массив уже в документе |
| обновление "купил еще" | MERGE одного ребра | $push в массив, тоже просто; но "кто купил товар" требует индекс по массиву или дублирование в документ товара |
| двухшаговый поиск | один шаблон MATCH, стоимость = число соседей | $lookup по массиву -> $unwind -> $lookup, декартово произведение на каждом шаге |
| путь 2..4 | `*2..4`, одно выражение | только цикл в приложении, несколько раундов запросов |
| рассинхронизация | нет, связь одна | если хранить и `bought` у покупателя, и `buyers` у товара, они разъедутся |

Вывод: для одношаговых запросов список id в документе не хуже, для двух и более шагов и обратного направления ребро выигрывает.

## Контрольные вопросы

1. Property graph - модель, где данные это узлы с метками и свойствами и направленные отношения между ними, у которых тоже есть тип и свойства
2. Узел - объект (товар, покупатель), отношение - связь между двумя узлами с типом и направлением, свойство - пара ключ-значение на узле или на отношении
3. Labels группируют узлы по роли (Customer, Product), по ним строятся индексы и с них начинается MATCH, чтобы не сканировать весь граф
4. CREATE всегда создает новый элемент, даже если такой уже есть. MERGE сначала ищет шаблон и создает только если не нашел
5. MATCH рисует шаблон как на бумаге: узел в круглых скобках, отношение в квадратных, стрелка задает направление. Neo4j ищет в графе все места, где шаблон совпадает
6. Направление - часть смысла: Customer купил Product, а не наоборот. С неверным направлением запрос вернет пустоту или не то. В MATCH можно идти против стрелки или без направления, но хранится ребро всегда направленным
7. Свойством - если по нему только фильтруют (цена, дата, город). Узлом - если объект участвует в связях и по нему нужно ходить: категория стала узлом, потому что товары связываются через нее и категории образуют дерево. Город оставил свойством, по нему пока никто не ходит
8. Два шага - связь через посредника: товары, которые покупали вместе; друзья друзей. Один шаг дает прямых соседей, два - уже рекомендации
9. Число путей растет экспоненциально с глубиной, через популярные узлы за 4-5 шагов достижим весь граф. Запрос без границы может съесть всю память и время
10. Для связей граф хранит ребра как указатели, переход по ребру стоит одинаково на любом размере базы. В документной модели каждый шаг - $lookup по индексу или отдельный запрос, и с глубиной цена растет

## Вывод

В этой лабе я спроектировал граф интернет-магазина для Neo4j от вопросов пользователей, а не от таблиц. Получилось три метки узлов (Customer, Product, Category) и четыре типа отношений (BOUGHT, VIEWED, BELONGS_TO плюс PART_OF для дерева категорий), 19 узлов и 33 ребра, созданные через MERGE под уникальными constraint. Написал запросы от простого MATCH до двухшаговых рекомендаций "кто купил то же, купили еще" и обхода переменной длины по категориям и по покупкам, посмотрел через PROFILE что поиск по sku идет через индекс, а по title через скан. Проверил изменение свойств узла и ребра, безопасное удаление с предварительным RETURN и то, что узел со связями удаляется только через DETACH DELETE. Главный плюс графа тут - запросы про связи пишутся одним шаблоном и не дорожают с ростом базы, минус - популярные товары становятся супер-узлами и обходы через них надо ограничивать по глубине и по дате, а просмотры лучше в графе долго не хранить.
